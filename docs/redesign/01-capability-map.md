# 01 — Capability Map: legacy PM workbook pack vs. existing LightPM

Assessed system: `C:\Users\DELL\WorkBuddy AI\lightweightpm` (LightPM) — Next.js App Router, Supabase/Postgres with a local-first SQLite/JSON mirror.
Requirements source: `lightpm-local/analysis-pack.md` (sections 7–11, 13, Appendix A).
Companion document: this pack's previous plan for one related feature is `docs/combine-report-plan.md`; it is reconciled explicitly in the rows marked **[CRP]** below.

Evidence convention: every verdict cites `path:line` from the assessed checkout. Where no evidence exists the row says **Unavailable** and names what was searched.

**Headline:** LightPM today is a *project + task* tracker with a configurable per-project task workflow. It has **no request/intake entity, no work-item type, no decision record, no approval engine, no master data, no alert engine, and no audit log outside tasks.** The nine capabilities that the pack treats as non-negotiable (pack §1.2) are almost entirely in the "Needs new development" band. The genuinely reusable assets are narrower but real: per-project configurable statuses with a management UI, a validated 0–100 progress field with an unused manual-override column, derived project health, a working-days-unaware overdue/attention model, standalone (project-less) tasks, role-scoped membership, and a type-validating, row-rejecting Excel importer.

Verdict values are exactly: `Reusable as-is` · `Configuration only` · `Needs extension` · `Needs new development` · `Unavailable`.

## 4. Requirements that cannot be confirmed from the supplied material

Stated plainly, as pack Appendix C requires:

1. **Platform role semantics.** `users.role` defaults to `member` and `admin` is checked in exactly one place (`app/api/health/schema/route.ts:55`). No route promotes a user to admin and registration never sets it (`app/api/auth/register/route.ts:51-55`), so the *intended* platform role model — and therefore whether a "portfolio coordinator" or "HOD" role is already contemplated — cannot be confirmed from the code.
2. **Whether `viewer` is meant to be enforced.** It is selectable and labelled "Read-only" (`components/ProjectSettingsModal.tsx:730`) but no read path consults it. Intent is unverifiable.
3. **Whether any deployment uses real Supabase or only the local mirror.** Two divergent schema sources exist (`schema.sql` vs `schema.sqlite.sql`) and the app tolerates drifting columns by design (`lib/resilientInsert.ts`), so the *effective* schema in any environment cannot be read off the checkout. This directly affects the cost of every "Needs extension" row.
4. **The `notifications` mock helpers' intent.** `getNotifications`/`markNotificationRead` are documented as "so callers (and any future UI) can rely on a uniform interface" (`lib/supabaseServer.ts:800-803`) with no caller. Whether an alert feature was started and abandoned, or is aspirational, is not determinable.
5. **Whether the eight seeded demo projects/tasks in the mock store are intended as sample data or as a fixture** (`lib/supabaseServer.ts` initial store). Nothing marks them synthetic, which is itself row 43.
6. **Retention and archival rules** (pack §14 deliverable 3 "history, retention"). `archived_at` exists on projects (`supabase/schema.sql:15`) but no retention, purge or legal-hold concept exists anywhere, and the pack gives no retention period — both sides are silent.
