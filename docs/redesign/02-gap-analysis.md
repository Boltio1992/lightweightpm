# 02 — Gap Analysis: legacy PM workbook pack vs. existing LightPM

Companion to `01-capability-map.md`. The capability map answers "can LightPM do this today?"; this document answers "what does it cost to close the distance, and what breaks if we do not?". Requirement references are to `lightpm-local/analysis-pack.md`; evidence references are to the LightPM checkout.

Complexity is relative delivery effort for a working, tested slice: **S** ≈ days, **M** ≈ 1–3 weeks, **L** ≈ 4+ weeks or cross-cutting. Per this pack's Appendix C, nothing below is approved scope — it is a priced menu.

---

## 1. Gap register

| Gap | Business impact | Recommended solution | Complexity (S/M/L) | Dependency | Risk |
|---|---|---|---|---|---|
| **1. No Request/intake entity** — demand cannot exist before approval; every item must be a project or a task (map row 1, `supabase/schema.sql:4-60`) | Portfolio cannot distinguish new demand from approved backlog, so "new demand vs planned" reporting (pack §2) and assessment lead time (§10.1) are unreportable; requesters must guess a delivery structure at submission time | Add a `requests` (intake) table as the front of the funnel — requester ref, requesting department, source, reference, scope, target application, decision status, linked delivery item — exactly the `requests` table the prior plan already specifies; keep projects/tasks as delivery objects and link rather than merge | M | Master data (gap 4) for department/application references; work-item type (gap 3) | Medium — the shape is pre-designed (`docs/combine-report-plan.md:115`), but request→project linking must be built before any UI, or the design will drift into a spreadsheet clone |
| **2. No decision/approval object** — approve/reject/defer/return/delegate have no representation anywhere (map row 19) | Approvals are unenforceable and unauditable; pack §9's rule that a transition "must not silently overwrite decision history" cannot be honoured; acceptance scenario A-07 ("decision, reason, actor, timestamp visible") fails outright | Add `approvals`/`decisions` (work item, requested by, approver, decision, reason, decided_at, resulting transition, delegation parent) plus the five verbs as explicit state transitions on the request/delivery lifecycle; surface as a queue, not as a Kanban column | L | Request entity (gap 1); typed audit (gap 5); role model (gap 9) | High — no approval semantics exist at all, so this is the largest single unknown; the temptation to model "approval" as a `Review` status (as the current schema does, `supabase/schema.sql:96-99`) will reproduce the exact conflation the pack forbids |
| **3. No work-item type registry** — a report request, change request, security initiative, automation and project are indistinguishable (map row 4) | Per-type forms, required fields, workflows, permissions and dashboards (pack §13 Q2, §8) are all blocked; every type-specific rule degenerates into a tag convention that reporting cannot be trusted on | One governed `work_item_types` table (key, label, base entity kind, required-field set, default workflow, permission set) plus a `type_id` on each work item; drive form and validation generation from it rather than branching in code | L | Decision on base-entity strategy (gap 1); per-project status model as the workflow substrate | High — the sequencing trap: build this before deciding whether requests and projects share a table and it will be rebuilt. Decide the base entity first |
| **4. No master data** — departments, teams, applications/services and locations do not exist (map rows 10–13) | Free-text org data, which is precisely the pack §7 defect that "spelling and abbreviation differences break reporting"; no dashboards by department, application or handling team are possible (§10.1); no department-scoped access (§13 Q12) | Four governed reference tables (organization units with parent/type, teams, applications/services with an owner, locations) plus nullable FKs on work items; admin CRUD UI with deactivate-not-delete; backfill from distinct importer values with an operator review step | M | None to create the tables; department-scoped access also needs gap 9 | Medium — schema is easy; the real cost is the cleansing/mapping workshop for existing free-text values, which needs business owners, not engineering |
| **5. Audit trail is partial, untyped and task-only** — six of twelve patchable task fields write no history; no project, membership or configuration history (map rows 21, 21a, 30) | Pack §13 Q11 and Appendix A-07/A-08 fail; the platform cannot answer "who changed this date and why"; compliance-grade traceability of approvals, assignments and configuration changes is absent | Extend `task_activity` semantics into a first-class `work_item_events` table with structured `field`, `old_value`, `new_value`, `actor_id`, `reason`, `occurred_at`, `event_kind` (transition/decision/assignment/config), written by a single server-side choke point for every covered table; keep the task timeline UI reading the same table | L | Request/delivery entities (gaps 1, 2) to have something to log against; a write choke point (see gap 8) | High — history is cheap only if it is captured at write time; every week without a choke point is a week of permanently lost history that cannot be reconstructed from the legacy workbook |
| **6. Decision status does not exist as a dimension** — lifecycle and health are separate, decision is not (map row 8) | A record can be lifecycle `In Delivery` while nobody knows whether it was approved; the pack §1.2 rule "do not use one status field for lifecycle, approval decision, health and progress" is violated by omission | Add explicit `decision_status` (Pending/Approved/Rejected/Deferred/Withdrawn/Returned for information) alongside the existing lifecycle-ish `status` and the computed health; do not overload `project_statuses` with decision values | S | Gap 2 for the decision record that justifies the value | Medium — low build cost, but it is a reporting-model change: existing four-value project statuses and five-value task statuses must be split into lifecycle vs decision, and every current view must be re-pointed |
| **7. Calculation of progress is ungoverned, stored override is inert** (map rows 8a, 9) | Three disagreeing percentages are one design decision away — the stored `projects.percent_complete`, the computed average of task percentages, and the legacy `technical Percent`; the pack's "preferably calculated with governed override" (§13 Q9) resolves to neither | Define one source of truth: calculated progress from tasks/milestones by default, with an override that is a governed record (value, reason, approver, expiry/review date) and never a bare column write; retire or wire up `projects.percent_complete` accordingly; reconcile the prior plan's `technical_percent` onto the same mechanism | M | Audit (gap 5) to record the override; decision on milestones (gap 18) | High — shipping both an editable percentage and a computed percentage without a rule guarantees that portfolio reporting contradicts delivery reporting, and the contradiction will be discovered by executives rather than by tests |
| **8. No persistence seam for new fields; writes fail silently** — the local mirror drops all constraints and `insertSkippingMissingColumns` omits unknown columns without failing (map row 32) | Every requirement in this document that adds a column inherits a silent-data-loss mode: a field can be accepted by the API, embedded in a "saved" response, and never stored. This is invisible in review and invisible in demo, and it is exactly the class of defect that destroys trust in a migration | Make schema drift a hard, visible failure in development and staging (`NOT NULL`/`UNIQUE`/FK in the mirror, typed column allow-list in TypeScript, generated types from the schema manifest, CI check of manifest vs migrations); keep lenient writes only behind an explicit production compatibility flag | M | None — do this first | High — this is the one gap that silently corrupts the output of every other fix. Highest urgency-to-cost ratio in the register |
| **9. Access control is session-only on the read paths and role-inconsistent on the write paths** — any authenticated user can read every project, read/edit/delete any task by id, and see all search results (map rows 22, 23, 23a) | Confidential records are exposed to every registered user; pack §1.2 (RBAC) and Appendix A-08 fail; assigning a `viewer` role gives a false assurance of read-only access | Centralise authorization: a `can(user, action, resource)` layer applied to every route, with project-membership scoping on all read queries, platform roles defined in a table (not a magic string), and the `viewer` role actually enforced; add confidentiality flag with field-level projection for sensitive attributes (requester id/position) | L | Master data for department scope (gap 4); platform role model, which cannot be inferred from the code (map §4.1) | High — some of these exposures are authn-only and trivially exploitable by any registered user; also needs a product decision on whether LightPM is single-tenant-by-trust or genuinely multi-team |
| **10. No alert engine, no working-day arithmetic, no escalation** (map rows 17, 18, 40) | Six of eight automation rules in pack §11 (MON-001…MON-008) cannot fire; escalation on missed follow-up dates (§6.1, A-06) does not happen; overdue detection exists but is naive 24-hour arithmetic, so "3 working days" and "within 10 working days" are both unimplementable | A scheduled rules job (cron/queue) over a business calendar (working days, holidays), a `notification` table with recipient/level/state, threshold configuration per rule, escalation ladders, and NOT NULL scheduling fields on work items; rules expressed as data (rule id, scope, predicate, threshold, action), not as code branches | L | Master data for owner/team routing (gap 4); operational item fields (gap 14); persistent notifications must stop being mock-only (`lib/localDb.ts:35`) | High — working-day escalation is a policy change as much as a build. Without a business calendar owner and an agreed escalation ladder, the engine will encode guesses that nobody owns |
| **11. Import cannot stage, map or reconcile** — commit-first, insert-only for tasks, reuse-by-name for projects (map rows 26, 27, 29) | A legacy migration cannot be run safely: no dry run, no mapping review, no duplicate suppression, no diff, no rollback. A second import silently doubles the task table. This blocks the entire pack §14 deliverable 8 and the prior plan's Phase 2 | Split import into profile → map → stage (staging tables with row-level disposition) → validate → reconcile (natural keys, e.g. `(source, ref_no)`) → commit → report, with rollback of a commit batch; make the column map and status map editable data, seeded from the existing `lib/importConfig.ts` aliases | L | Persistent reference/reference-number scheme (gaps 1, 25) so rows have stable natural keys | High — the prior plan already committed to preview-before-commit and upsert and neither exists (`docs/combine-report-plan.md:118`), so this gap is already on the critical path of an agreed feature and cannot be deferred as "migration work later" |
| **12. Human-readable references do not exist** (map row 33) | Users cannot reference a work item in conversation, email or a steering deck; there is no stable external key for reconciliation, so import matching must rely on mutable titles and names (which is why gap 11 is unsolvable without this) | A per-type, per-year reference sequence (`REQ-2026-0001`, `PRJ-001`, `STD-001`, `OPS-001`) generated server-side, immutable and unique, exposed in list/detail/export and used as the import natural key | S | Work-item type (gap 3) for per-type prefixes | Low build risk, high sequencing value — do it before reconciliation, not after |
| **13. Standalone operational items lack the semantics the pack requires** (map row 20) | Project-less tasks exist, but with no support owner, next action, follow-up date, outcome or escalation, so the Operational Follow-up sheet has no honest destination; A-06 fails | Either add an operational work-item kind (owner, next action, follow-up date, outcome, status, activity) or extend tasks with those governed fields plus a clear rule for when a task may be promoted to a delivery item; keep both linked to a request/project when one exists | M | Alert engine (gap 10) for follow-up breaches; audit (gap 5) | Medium — the cheap answer ("just use tasks") is defensible, but only if the follow-up date is a real governed field rather than the task `due_date`, whose meaning already differs |
| **14. No study/assessment phase and no conversion link** (map rows 6, 7) | Initiatives cannot be tracked before implementation approval, and study completion cannot be separated from delivery progress; the pack §5 behaviours to preserve (record recommendation/decision, convert without retyping, retain study↔delivery links) are all absent; A-02 fails | Add an assessment/study record owned by the requester's pipeline with its own state, owner, target quarter, dates, recommendation and decision; a conversion action copies approved fields into a delivery item and writes a typed link both ways, reusing the importer's existing two-pass link resolution pattern | M | Request entity (gap 1); decision record (gap 2) | Medium — the link model must be decided once and shared with the release→request case the prior plan requires, or two incompatible link mechanisms will appear |
| **15. Service-level fields are dropped rather than governed** — active columns exist in the schema but are ignored or constraint-free | Active losses found in code: `projects.percent_complete` is never read by the health computation or dashboard (writes are silently meaningless); task `priority` is unvalidated free text; task `status` accepts any string through the API, so a typo creates an invisible orphan status that no board renders and no report counts | Add server-side validation for every enumerated field against governed values; make `percent_complete` either authoritative or removed; migrate orphan status values; fail loudly on unknown enum input rather than storing it | S | Enum values must first move out of their four hard-coded locations (`types/index.ts:107-113`, `app/api/projects/[id]/statuses/route.ts:8-14`, `components/TaskInspector.tsx:360-366`, `lib/importConfig.ts:78-93`) | Medium — low effort, but it will surface existing bad rows; without a migration/backfill plan the fix creates a support problem |
| **16. Dates are weak: no conflict detection, no quarter, no timezone, no explicit unknown state** (map rows 31, 39) | The pack's §7 concerns — "dates and quarters can conflict", "invalid dates reduce trust", "missing fields imply meaning" — all hold: `end < start` is accepted, quarters are never derived, and a null date means simultaneously "not set", "not applicable" and "unknown" | Validate `end >= start` and dependent dates server-side, derive quarter from target dates, store an explicit `Not Applicable`/`Unknown` sentinel or companion flag for the fields that need it, and decide and document timezone semantics for date storage | S | Enum/validation work (gap 15); a decision on timezone is a product decision | Low — mostly mechanical; the only real risk is re-deciding timezone late, after data exists |
| **17. No confidentiality or field-level visibility** (map row 24) | Sensitive attributes (requester staff identity, position, branch) are stored and returned with no classification, no redaction and no field projection; pack §1.2 and A-08 fail | A confidentiality classification on work items, a permission table mapping role→field visibility, projection on every read and search path, and redaction of identity fields for non-privileged viewers; log reads of confidential records in the audit stream | L | Auth layer (gap 9); audit (gap 5) | High — touches every read path, and cannot be retrofitted safely once a search index or export has leaked data |
| **18. No milestone, risk/issue or dependency entities** (map rows 34–36) | Milestone-based health and progress (pack §8, §10.3) cannot be computed; blockers cannot be tracked with an owner, severity and response, so MON-004 ("escalate with dependency and blocker details") has no details to escalate; "milestones due soon or overdue" is unreportable | Add three small entities (milestone with planned/actual date and contribution to progress; risk/issue with owner, severity, response, due date, escalation; dependency as a typed link between items or to an external factor), and feed milestone dates into both the calculated progress rule (gap 7) and health | M | Progress source-of-truth decision (gap 7); alert engine (gap 10) for milestone/dependency breaches | Medium — individually small, collectively they change the health and progress model, so they must land after, not before, the gap 7 decision |
| **19. No export and no report-shaped read path** (map row 42; prior plan §2, §3 Phase 3) | The prior plan's committed deliverable — export in exactly the `Combine Report` column order — has no implementation; the only xlsx endpoint emits an empty template, so migration reconciliation reports and steering-pack extracts must be rebuilt by hand | A governed export endpoint (server-side, typed, ordered columns, filter parameters mirrored from the list view) reusing the same query layer as the UI so export and screen cannot diverge; include injected columns such as source, reference, decision and calculated progress | M | Reference scheme (gap 12); the target report shape must be frozen first | Medium — export is where conflation becomes public: every field whose meaning is ambiguous (two statuses, three percentages) will be visibly wrong in a spreadsheet that executives read |
| **20. Portfolio-scale aggregation is in-memory** (map row 42) | Every dashboard and project-list request loads all tasks and all projects into application memory and aggregates in JavaScript; fine at demo scale, but latency and memory grow with the whole portfolio rather than with the page, so a real backlog makes the dashboard the slowest page in the product | Push aggregation into SQL views/materialised views keyed on portfolio filters, add indexes for the aggregating dimensions (stage, type, team, application, due date, updated_at), paginate the list/attention queries, and keep one implementation shared by page and API | M | Only worth doing after types/master data exist (gaps 3, 4), since the aggregating dimensions are the ones being added | Medium — premature optimisation now would aggregate over dimensions that are about to change; deferring too long risks the dashboard becoming unusable exactly when adoption starts |
| **21. Updates and narrative are unstructured** (pack §7 "narrative comments hold key actions") | Comments and prose activity `details` are the only place decisions, blockers and next actions can currently be recorded, so nothing is filterable, alertable or reportable; the dashboard already resorts to substring-matching a prose string to count completions (`lib/dashboard.ts:186`) | Promote structure beside the narrative: structured next action, blocker, outcome and decision fields on updates; keep free-text comments for conversation; migrate nothing from history, but stop new key actions from landing only in prose | S | Operational item fields (gap 13); audit (gap 5) | Low — but it only pays off if the UI actively discourages burying a decision in a comment |
| **22. Synthetic/test-data governance is absent** | Pack §12's `dataClassification = SYNTHETIC` marker and the prohibition on deploying synthetic seed data to production have no counterpart; the mock store seeds unmarked demo rows with no production guard | Add the `dataClassification` marker to every seeded dataset, gate seeding behind an explicit environment flag, and fail startup if synthetic data is detected against a production configuration | S | None | Low build risk, real reputational risk if demo rows reach a real portfolio; a two-line guard against a class of embarrassing incident |
| **23. Retention, archival and purge rules are undefined on both sides** (map §4.6) | `archived_at` exists for projects and nothing else; there is no retention period, no legal hold and no purge path, so the platform cannot answer pack §14 deliverable 3's retention requirement, and deleting a task cascades its history away irrecoverably | Decide retention per entity with data owners, implement archive-before-delete with history preservation (soft delete, no cascading history removal), and document the policy in the target model | M | Audit (gap 5) for the preserved history; a business decision on retention | Medium — mostly a governance decision, but hard-delete cascades make today's behaviour actively destructive, so at minimum stop destroying history before the policy lands |
| **24. Priority is a hard-coded, unvalidated, partially-present dimension** (map row 14) | Pack MON-001 ("high-priority request remains Under Review…") cannot be scoped to priority on the request side because requests do not exist, priorities are tasks-only, and the allowed set is duplicated in four places with no server-side validation | Promote priority to governed master data (configurable levels, ordering, colour, optional SLA consequence), validate on write, and apply it to every work-item type, not just tasks | S | Work-item type (gap 3) so priority exists on requests/projects too; alert engine (gap 10) to consume it | Low — small and mechanical; the only trap is choosing a fixed four-level enum now and having to migrate it later, so make it data |

## 2. Top 10 gaps by consequence

Ordered by how much damage the gap does if left open, not by build order.

1. **Writes can silently drop fields.** `insertSkippingMissingColumns` omits columns the database does not have and the local mirror enforces no constraints (`lib/resilientInsert.ts:1-111`, `supabase/schema.sqlite.sql:11-24`), so a field can be accepted by the API, reported as saved, and never stored — which quietly invalidates the output of every other fix in this register.
2. **There is no Request entity, so there is no intake.** Demand cannot exist before approval and the pack's own headline dashboard split (new/unplanned demand versus planned portfolio) is unreportable at all (map row 1).
3. **There is no approval or decision record.** Approve, reject, defer, return and delegate have no representation anywhere in the schema or API, so governance is unenforceable and Appendix A-07 fails outright (map row 19).
4. **The audit trail is partial, untyped and task-only.** Six of twelve patchable task fields write no history, no project or configuration change is logged, and previous/new values live inside prose strings, so "who changed this and why" is unanswerable and every week of delay permanently loses history (map rows 21, 21a, 30).
5. **Any authenticated user can read every project and edit or delete any task by id.** Reads are session-only, the `viewer` role is UI-only, and there is no confidentiality flag, so pack §1.2 and Appendix A-08 both fail and the exposure is trivially reachable today (map rows 22, 24).
6. **Import cannot stage, map or reconcile.** The importer commits on upload and always inserts tasks, so a second import silently duplicates the task table and a legacy migration has no dry run, no diff and no rollback (map rows 26, 29).
7. **Progress has three potential answers and no rule.** The stored `projects.percent_complete` is never read, the API computes a mean of task percentages, the dashboard computes done-over-total, and the legacy `technical Percent` would be a fourth, so portfolio and delivery reporting are set up to contradict each other (map rows 8a, 9).
8. **No alert engine and no working-day arithmetic.** Six of the eight automation rules in pack §11 cannot fire and escalation on missed follow-up dates does not exist, because elapsed time is naive 24-hour millisecond maths and notifications live only in an in-memory mock with no table and no caller (map rows 17, 18, 40).
9. **No master data for departments, teams, applications or locations.** Organization data can only be free text, which is precisely the pack §7 defect that breaks reporting, and it also blocks every department- or team-scoped dashboard and permission (map rows 10–13).
10. **No work-item type, so the pack's central normalization requirement is unmet.** A report request, change request, security initiative, automation and project are indistinguishable, which blocks per-type forms, required fields, workflows and permissions and leaves the platform unable to express anything the legacy workbook distinguishes by a `Type` column (map row 4).

## 3. Recommended sequencing (why this order, not the consequence order)

| Stage | Contents | Rationale |
|---|---|---|
| **0. Stop the leaks** — gaps 8, 15, 16, 22 | Hard schema discipline in dev/staging, enum validation, date cross-validation, synthetic-data marker | Cheap, unblocks everything, and every later stage writes through this layer |
| **1. Foundation identities** — gaps 1, 3, 4, 12 | Request entity, type registry, master data, human-readable references | Everything downstream references these; getting them late means rebuilding links and re-importing |
| **2. Governance core** — gaps 2, 5, 6 | Decision/approval records, structured audit choke point, decision-status dimension | These are the pack's non-negotiables and they must exist before any workflow is allowed to change state |
| **3. One source of truth for progress and status** — gaps 7, 18, 24 | Calculated progress with governed override, milestones, governed priority | Resolves the conflation risk while the data volume is still small |
| **4. Operational reality** — gaps 13, 14, 10, 17 | Operational items, study/assessment + conversion, alert engine with business calendar, confidentiality | Needs owners from stages 1–2 for routing, escalation and visibility |
| **5. Migration and reporting** — gaps 11, 19, 20, 21, 23 | Staged/reconciling import, governed export, SQL-side aggregation, structured updates, retention policy | Import is worthless before natural keys and mapping data exist; export is worthless before field meanings are unambiguous |

**Do not start with the dashboard.** Every dashboard requirement in pack §10 depends on dimensions (type, department, team, application, decision, stage-entered timestamp) that stages 0–2 create. Building dashboards first guarantees they are rebuilt, and it defers the two gaps whose cost grows with delay: silent write loss (gap 8) and missing audit history (gap 5).
